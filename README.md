# harness-lab

> 신뢰 불가능한 LLM을 신뢰 가능한 시스템으로 감싸는 오케스트레이션 레이어를
> **프레임워크 없이, 손으로** 짜보며 harness engineering을 학습하는 프로젝트.

로컬 ollama(`qwen3:8b`, `phi4-mini`)를 대상으로 ReAct 제어 루프를 밑바닥부터 구현한다.
목표는 "코딩 에이전트 제품"이 아니라 **임의의 LLM을, 임의의 도메인에서, 신뢰 가능하게
동작시키는 오케스트레이션 레이어를 설계·검증하는 역량**이다. 도메인 tool은 일부러 장난감을
쓴다(도메인이 아니라 harness 자체의 견고함에 집중하기 위해).

---

## 핵심 원칙 (전 단계 관통)

- **프레임워크 금지.** LangChain/LlamaIndex류 안 씀. `net/http` + `encoding/json`으로 ollama에 직접 붙는다. 망가진 응답의 날것을 봐야 배운다.
- **모델 불가지론.** 트랜스포트를 인터페이스 뒤에 두고 `qwen3:8b` ↔ `phi4-mini`를 control 변수로 갈아끼운다. "더 좋은 harness가 더 약한 모델을 얼마나 보상하는가"가 이 프로젝트의 진짜 측정값.
- **에러는 관찰(observation)이다.** 실패를 루프를 죽이는 예외가 아니라 모델에게 다시 먹이는 입력으로 다룬다. 이게 ReAct의 핵심 통찰.
- **관측성 우선.** 비결정적 루프는 매 턴의 구조화된 트레이스 없이는 디버깅이 불가능하다. 처음부터 찍는다.

## 권장 디렉토리 레이아웃

```
harness-lab/
├── README.md
├── go.mod
├── cmd/
│   └── harness/
│       └── main.go          # 진입점: 태스크 하나 받아 루프 실행
├── internal/
│   ├── transport/           # ollama /api/chat 통신 (인터페이스 + 구현)
│   ├── tools/               # tool 레지스트리 + 디스패치 + 토이 tool들
│   ├── validate/            # args ↔ JSON schema 검증
│   ├── agent/               # 제어 루프 (종료·재시도·budget)
│   └── trace/               # 구조화 로깅
└── testdata/
    └── tasks.json           # 체이닝 강제 태스크셋 (M8, 이후 eval harness의 씨앗)
```

> 처음부터 다 만들지 말 것. 디렉토리는 마일스톤이 진행되며 자라난다. M1은 `main.go` 한 파일로 시작해도 된다.

## 마일스톤

진행하며 `[ ]` → `[x]`로 체크.

### M0 — 셋업 & raw 응답 관찰
- [ ] `go mod init` + repo 초기화
- [ ] ollama 가동 확인: `ollama list`에 `qwen3:8b`, `phi4-mini`가 보이는지
- [ ] `net/http`로 `POST /api/chat`에 메시지 하나 보내고 응답 **raw JSON을 그대로 출력**
- [ ] `tools` 배열(JSON schema 함수 정의)을 넣고 모델이 `message.tool_calls`로 응답하게 만들기
- [ ] qwen3와 phi4-mini의 응답 JSON 모양 **차이를 직접 눈으로 비교** (arguments가 객체인지 문자열인지, tool_call_id 유무 등)

**배우는 것:** ollama의 실제 응답 계약. 문서가 아니라 본인 버전이 진실. SDK를 붙이기 전에 날것을 봐야 이후 파싱 결정의 근거가 생긴다.
**완료 기준:** 같은 프롬프트에 두 모델의 raw 응답을 나란히 찍어서 차이를 한 문장으로 적을 수 있다.

### M1 — 최소 happy-path 루프
- [ ] tool 1개(`get_current_time`)만 등록
- [ ] 루프 구현: `chat → tool_calls 있으면 실행하고 결과를 append → 다시 chat → 없으면 종료`
- [ ] assistant 턴과 tool 결과를 messages에 누적하는 흐름 완성
- [ ] **에러 처리 일절 없이** end-to-end로 한 번 돌려보기

**배우는 것:** happy path는 30줄이면 끝난다는 사실. 이게 baseline이고, 이후 모든 단계는 "이 30줄을 신뢰 가능하게 만드는 것".
**완료 기준:** "지금 몇 시야?" → tool 호출 → 자연어 답변까지 한 번에 흐른다.

### M2 — tool 레지스트리 + 디스패치 (경계 만들기)
- [ ] tool을 `{name, description, schema, handler}`로 추상화
- [ ] 이름으로 핸들러를 찾아 실행하는 레지스트리/디스패처
- [ ] 토이 tool 2~3개로 확장: `calculator`, `get_current_time`, mock `search`(캔드 데이터 반환)
- [ ] 루프 코드에서 tool 구현 세부를 분리 (루프는 tool이 뭔지 몰라야 함)

**배우는 것:** "스크립트"와 "harness"를 가르는 abstraction boundary. tool을 데이터로 다루기 시작하면 도메인 교체가 공짜가 된다.
**완료 기준:** 새 tool을 추가할 때 루프 코드를 한 줄도 안 건드린다.

### M3 — 검증 레이어 (실행 전 방어)
- [ ] 호출된 tool 이름이 레지스트리에 **존재하는지** 검증
- [ ] arguments를 tool의 **JSON schema로 검증** (필수 필드 누락, 타입 오류)
- [ ] 검증 실패 시 **절대 핸들러를 실행하지 않음**

**배우는 것:** 쓰레기로 부작용을 일으키지 않기. 검증은 실행 *전에*.
**완료 기준:** 잘못된 인자로 호출이 와도 핸들러가 호출되지 않고, 검증 에러가 구조화되어 잡힌다.

### M4 — 에러를 관찰로 (복구 루프)
- [ ] 존재하지 않는 tool 호출(환각) → "유효한 tool 목록"을 에러로 다시 먹여 재시도
- [ ] schema 위반 → 검증 에러 메시지를 모델에게 다시 먹임
- [ ] 깨진/펜스로 감싼 tool call → 검출 + 재프롬프트(또는 관대한 파서). **구조 강제 vs 관대한 파싱** 중 본인 선택을 기록
- [ ] tool 핸들러 자체의 throw(네트워크, 잘못된 입력) → 루프를 죽이지 말고 `"Error: ..."`로 감싸 관찰로 전달

**배우는 것:** 약한 모델이 사방에서 깨질 때 harness가 어떻게 자가 복구하는가. 실패를 입력으로 되먹이는 패턴.
**완료 기준:** 일부러 망가진 응답을 주입해도 루프가 죽지 않고 복구를 시도한다.

### M5 — 종료 & budget (가장 어려운 부분)
- [ ] `max iterations` 상한
- [ ] 무한 반복 검출: tool `name + args` 해시로 중복 호출 감지 → 끊거나 nudge 주입
- [ ] tool을 안 쓰고 답해버리는 경우 / 끝났는데 종료 선언 안 하는 경우 처리
- [ ] (선택) 토큰/호출 budget 개념 도입

**배우는 것:** 정지 조건은 본질적으로 난제다. 비결정적 에이전트의 안전한 종료 설계.
**완료 기준:** 무한 루프에 빠지지 않고, 상한에 걸리면 깔끔히 멈추며 그 이유가 트레이스에 남는다.

### M6 — 모델 불가지론 트랜스포트 + qwen3 thinking 처리
- [ ] 트랜스포트를 인터페이스로 추출, 플래그/설정으로 모델 교체 가능하게
- [ ] qwen3:8b의 `<think>` 트레이스를 **로깅엔 남기되 파싱에선 분리**
- [ ] phi4-mini로 같은 태스크를 돌려 thinking 모드가 없는 대조군 확인
- [ ] phi4-mini의 빈약한 tool calling이 어디서 더 깨지는지 기록

**배우는 것:** 추론 트레이스와 실행 가능한 출력의 분리. 모델별 특성을 harness가 흡수하는 법.
**완료 기준:** 코드 변경 없이 플래그만으로 두 모델을 바꿔 끼울 수 있다.

### M7 — 관측성 (구조화 트레이스)
- [ ] 매 iteration을 구조화 레코드로 기록: 보낸 messages / 받은 raw 응답 / 파싱 결과 / 검증 결과 / 실행한 tool과 결과 / 소요 시간
- [ ] 한 번의 태스크 실행 = 읽을 수 있는 trace 하나 (JSON lines 또는 콘솔 pretty print)
- [ ] 실패한 실행을 trace만 보고 원인 진단해보기

**배우는 것:** 분산 시스템에서 신뢰 불가 컴포넌트를 감싸는 것과 동일한 문제(재시도·멱등성·타임아웃·트레이싱)가 전부 여기로 매핑된다. 사람들이 가장 많이 건너뛰고 가장 많이 후회하는 부분.
**완료 기준:** "왜 이 실행이 실패/반복했는가"를 코드를 다시 안 읽고 trace만으로 답할 수 있다.

### M8 — 체이닝 태스크로 통합 검증
- [ ] 멀티스텝을 **강제하는** 태스크 작성. 예: "오늘부터 8월 OMSCS 마감까지 며칠인지 계산하고 거기에 3을 곱해라" (time tool → calculator tool 체이닝 필요)
- [ ] 같은 태스크를 qwen3 / phi4-mini 양쪽으로 실행
- [ ] 두 모델의 성공 여부·재시도 횟수·실패 지점을 비교 기록
- [ ] 태스크 3~5개를 `testdata/tasks.json`에 모아두기

**배우는 것:** harness가 약한 모델을 얼마나 보상하는지 처음으로 체감. 그리고 이 태스크셋이 다음 프로젝트(eval harness)의 씨앗이 된다.
**완료 기준:** 동일 태스크에서 두 모델의 행동 차이를 숫자/관찰로 비교한 메모가 있다.

## 다음으로

M8에서 "이 harness 변경이 실제로 도움이 됐나?"를 숫자로 답하고 싶어지는 순간이 온다.
그게 **eval harness**(태스크셋 + 자동 채점 + harness 버전 간 회귀 추적)로 넘어가는 신호다.
`testdata/tasks.json`이 그 출발점이고, harness-lab의 자연스러운 확장이 된다.

코딩 에이전트(Claude Code류) 방향으로 키우려면: 토이 tool을 `read_file`/`edit_file`/`run_bash`
같은 **부작용 있는 실제 tool**로 교체하고, 그 위에 권한·승인 레이어(M5의 확장)와
코드베이스 규모의 컨텍스트 관리(요약·축출·검색)를 얹으면 된다. 골격은 이미 M1~M7에 다 있다.
