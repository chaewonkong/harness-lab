# harness-lab

> 신뢰 불가능한 LLM을 신뢰 가능한 시스템으로 감싸는 오케스트레이션 레이어를
> **프레임워크 없이, 손으로** 짜보며 harness engineering을 학습하는 프로젝트.

로컬 ollama(`qwen3:8b`, `phi4-mini`)를 대상으로 ReAct 제어 루프를 밑바닥부터 구현한다.
목표는 "코딩 에이전트 제품"이 아니라 **임의의 LLM을, 임의의 도메인에서, 신뢰 가능하게
동작시키는 오케스트레이션 레이어를 설계·검증하는 역량**이다. 도메인 tool은 일부러 장난감을
쓴다(도메인이 아니라 harness 자체의 견고함에 집중하기 위해).

각 마일스톤은 **할 일**(무엇을 만드는가)과 **생각해볼 것**(어떻게 설계할지는 본인 판단)으로
나뉜다. 후자는 정답을 주지 않는다 — 직접 결정하고 그 근거를 트레이스/메모로 남기는 게 학습이다.

## 멘탈 모델 (먼저 잡고 갈 것)

- **ollama는 본인 Go 함수를 호출하지 못한다.** 모델은 "이 함수를 이런 인자로 불러라"는 *제안*(JSON)만 뱉는다. 실제 실행은 100% 본인 Go 앱이 한다. 이 비대칭이 검증·권한·종료(M3~M5)가 성립하는 이유다 — 본인 코드가 게이트키퍼다.
- **harness-lab은 학습 단계엔 서버가 아니라 CLI다.** ollama 서버(mini PC, `:11434`)에 HTTP로 붙는 *클라이언트*다. 호출 방향은 `harness-lab → ollama`이지 그 반대가 아니다.
- **개발 구도:** macbook에서 `go run`으로 harness-lab을 돌리고, Tailscale IP로 mini PC의 ollama를 때린다. "서버로 배포"는 Telegram 등 상시 프론트엔드를 붙이는 M9(선택)에서나 등장한다.

```
[harness-lab (Go CLI, macbook)]  ── HTTP ──>  [ollama @ <tailscale-ip>:11434 (mini PC)]
        ↑ 함수 실행은 여기서 (게이트키퍼)              ↑ 모델은 "제안"만 한다
```

---

## 핵심 원칙 (전 단계 관통)

- **프레임워크 금지.** LangChain/LlamaIndex류, godotenv 같은 편의 패키지도 안 씀. 표준 라이브러리(`net/http`, `encoding/json`)로 ollama에 직접 붙는다. 배우려는 추상화를 `go get`으로 덮지 않는다.
- **모델 불가지론.** 트랜스포트를 인터페이스 뒤에 두고 `qwen3:8b` ↔ `phi4-mini`를 control 변수로 갈아끼운다. "더 좋은 harness가 더 약한 모델을 얼마나 보상하는가"가 이 프로젝트의 진짜 측정값.
- **에러는 관찰(observation)이다.** 실패를 루프를 죽이는 예외가 아니라 모델에게 다시 먹이는 입력으로 다룬다. 이게 ReAct의 핵심 통찰.
- **관측성 우선.** 비결정적 루프는 매 턴의 구조화된 트레이스 없이는 디버깅이 불가능하다. 처음부터 찍는다.

## 마일스톤

진행하며 `[ ]` → `[x]`로 체크.

### M0 — 정찰: ollama의 실제 응답 계약 확인

코드 프로젝트가 아니라 **정찰**이다. 앞으로 본인 클라이언트가 상대할 서버가 실제로 어떤 JSON을
주는지 눈으로 확인하는 단계. 문서가 아니라 *본인 버전의 ollama*가 진실이다. 여기서 본 것이
M1부터 짤 struct와 파싱 결정의 근거가 된다.

**할 일**
- [ ] `go mod init`, repo 초기화, `.gitignore`에 `.env` 추가
- [ ] `OLLAMA_URL`을 `.env`로 관리하고 **런타임에만 주입**(zshrc 안 건드림). 표준 라이브러리로 `.env`를 직접 읽거나, `env $(grep -v '^#' .env | xargs) go run ...` 방식 중 택1
- [ ] 원격 ollama 생존 확인: `curl http://<tailscale-ip>:11434/api/tags` (← `ollama list`의 HTTP판). `qwen3:8b`, `phi4-mini`가 보이는지
- [ ] `/api/chat`에 user 메시지 1개 + `tools` 배열 1개(예: `get_current_time`)를 넣어 보내고, 응답 **raw JSON을 그대로 출력**. 모델이 `content` 대신 `tool_calls`를 주는 걸 확인
- [ ] `model` 필드만 바꿔 qwen3 / phi4-mini 응답을 **나란히** 받아보기

**생각해볼 것**
- `arguments`가 파싱된 객체로 오나, 문자열로 오나? → Go에서 `map[string]any`로 받을지, `json.RawMessage`로 받을지가 갈린다
- `tool_call_id` 같은 필드가 있나? 없다면 나중에 여러 tool 호출이 동시에 왔을 때 결과를 무엇으로 매칭할 건가?
- phi4-mini가 `tool_calls`를 제대로 주나, 아니면 "get_current_time을 부르겠습니다"라고 산문으로 흘리나?
- qwen3의 추론 트레이스(`<think>`)는 어디에 담겨 오나 — 별도 필드인가, `content` 안인가?

> mini PC의 ollama가 `127.0.0.1`에만 바인딩돼 있으면 Tailscale IP로 안 들어온다. mini PC 쪽에서 `OLLAMA_HOST=0.0.0.0:11434`로 서빙돼야 한다(mini PC 한정 설정).

**완료 기준:** 두 모델의 raw 응답을 나란히 놓고 위 네 가지 차이를 메모로 적을 수 있다.

### M1 — happy-path 루프

이상 동작을 전혀 가정한 채, 정상 경로만 끝까지 흐르게 한다. 이 30줄 남짓이 baseline이고,
이후 모든 마일스톤은 "이걸 신뢰 가능하게 만드는 것"이다. 그러니 **지금은 일부러 방어하지 않는다.**

**할 일**
- [ ] tool 1개(`get_current_time`)만 등록
- [ ] 루프: `chat → tool_calls 있으면 실행하고 결과를 append → 다시 chat → tool_calls 없으면 그 content가 최종 답`
- [ ] assistant 턴과 `{role: "tool", ...}` 결과를 messages에 누적하는 흐름 완성
- [ ] **에러 처리 없이** "지금 서울 몇 시야?"가 end-to-end로 한 번 흐르는 것 확인

**생각해볼 것**
- tool 실행 결과를 모델에게 돌려줄 때 어떤 메시지 모양으로 넣어야 모델이 "이건 내가 부른 함수의 결과"라고 이해하나? (M0에서 본 `tool_call_id` 유무가 여기서 걸린다)
- 종료 조건을 무엇으로 판정하나 — "tool_calls가 비어있음"이 유일한 신호인가?
- messages 누적 순서가 틀리면 모델이 혼란스러워한다. assistant 턴을 먼저 넣나, tool 결과를 먼저 넣나?

**완료 기준:** 한 번의 tool 호출이 필요한 질문이 호출 → 실행 → 자연어 답변까지 끊김 없이 흐른다.

### M2 — tool 레지스트리 + 디스패치 (경계 만들기)

"스크립트"와 "harness"를 가르는 건 abstraction boundary다. tool을 하드코딩된 if/switch가 아니라
*데이터*로 다루기 시작하면, 도메인 교체가 거의 공짜가 된다.

**할 일**
- [ ] tool을 `{name, description, schema, handler}` 형태로 추상화
- [ ] 이름으로 핸들러를 찾아 실행하는 레지스트리/디스패처
- [ ] 토이 tool 2~3개로 확장: `calculator`, `get_current_time`, mock `search`(캔드 데이터 반환)
- [ ] 루프 코드가 tool의 구체 구현을 모르게 분리

**생각해볼 것**
- handler의 시그니처를 어떻게 잡을 건가? 인자가 tool마다 다른데 — `func(json.RawMessage) (string, error)`처럼 통일할 건가, 아니면 다른 방식인가?
- tool의 JSON schema를 Go 코드 어디에 두나? 핸들러 옆에 같이 두면 ollama로 보낼 `tools` 배열을 레지스트리에서 자동 생성할 수 있다 — 이 자동 생성을 할 건가?
- "루프는 tool이 뭔지 몰라야 한다"는 원칙을 어디까지 지킬 건가? 완벽한 격리 vs 실용적 타협의 선

**완료 기준:** 새 tool을 추가할 때 레지스트리에 등록만 하면 되고, 루프 코드는 한 줄도 안 건드린다.

### M3 — 검증 레이어 (실행 전 방어)

본인 코드가 게이트키퍼라는 멘탈 모델이 처음으로 코드가 되는 지점. 모델의 "제안"을 *실행하기 전에*
믿을 수 있는지 검사한다. 쓰레기로 부작용을 일으키지 않는 게 핵심.

**할 일**
- [ ] 호출된 tool 이름이 레지스트리에 **존재하는지** 검증
- [ ] arguments를 해당 tool의 **JSON schema에 맞춰 검증**(필수 필드 누락, 타입 오류)
- [ ] 검증 실패 시 **핸들러를 절대 실행하지 않고**, 구조화된 검증 에러를 만든다

**생각해볼 것**
- JSON schema 검증을 어디까지 직접 짤 건가? 라이브러리 금지 원칙상 손으로 짜야 하는데 — 필수 필드 + 타입 체크 정도의 최소 검증으로 시작할지, 더 갈지. 과도하게 일반적인 schema validator를 만들려다 본질을 놓치지 말 것
- 검증 에러를 어떤 *구조*로 표현하나? 이 구조가 M4에서 모델에게 되먹일 메시지의 재료가 된다 — 미리 그걸 염두에 두고 설계
- 검증은 트랜스포트 레이어인가, 디스패치 레이어인가, 별도 레이어인가? 경계를 어디 둘지

**완료 기준:** 잘못된 인자나 없는 tool 이름이 와도 핸들러가 호출되지 않고, 실패가 구조화된 에러로 잡힌다.

### M4 — 에러를 관찰로 (복구 루프)

약한 모델은 사방에서 깨진다. 그 실패를 루프를 죽이는 예외가 아니라 **모델에게 다시 먹이는 입력**으로
다루는 게 ReAct의 핵심 통찰이다. M3에서 만든 검증 에러가 여기서 비로소 모델에게 흘러간다.

**할 일**
- [ ] 존재하지 않는 tool 호출(환각) → "유효한 tool은 이것들"을 관찰로 되먹여 재시도
- [ ] schema 위반 → M3의 검증 에러 메시지를 모델에게 되먹임
- [ ] 깨진/마크다운 펜스로 감싼 tool call → 검출 후 처리
- [ ] tool 핸들러 자체의 실패(네트워크, 잘못된 입력) → 루프를 죽이지 말고 `"Error: ..."`로 감싸 관찰로 전달

**생각해볼 것**
- **이 프로젝트의 첫 큰 설계 분기:** 모델이 형식을 어기면 *재프롬프트로 강제*할 것인가(structure-first), *관대한 파서로 받아낼* 것인가(lenient parsing)? 둘은 트레이드오프가 다르다. 본인 선택과 근거를 반드시 기록
- 되먹이는 에러 메시지를 어떻게 쓰면 모델이 실제로 고치나? 너무 짧으면 못 고치고, 너무 길면 컨텍스트를 잡아먹는다
- 복구를 몇 번까지 시도하나? 같은 에러가 반복되면? (M5와 맞닿는 지점)

**완료 기준:** 일부러 망가진 응답(없는 tool, 깨진 args)을 유발해도 루프가 죽지 않고 복구를 시도한다.

### M5 — 종료 & budget (가장 어려운 부분)

정지 조건은 본질적으로 난제다. 비결정적 에이전트를 안전하게 멈추는 설계.

**할 일**
- [ ] `max iterations` 상한
- [ ] 무한 반복 검출: 같은 tool을 같은 인자로 반복 호출하는 것을 감지 → 끊거나 nudge 주입
- [ ] 써야 할 tool을 안 쓰고 답해버리거나, 끝났는데 종료를 선언 안 하는 경우 처리
- [ ] (선택) 호출 횟수/토큰 budget 개념 도입

**생각해볼 것**
- "같은 호출의 반복"을 무엇으로 판정하나? `name + args`의 해시? 그런데 정당하게 같은 tool을 다른 맥락에서 두 번 부를 수도 있다 — 어떻게 구분하나?
- 상한에 걸렸을 때 어떻게 끝내나? 그냥 멈추나, 마지막으로 "지금까지로 답하라"고 한 번 더 요청하나?
- nudge(슬쩍 찌르는 시스템 메시지) 주입이 약한 모델에게 실제로 먹히나? qwen3와 phi4-mini가 다르게 반응할 것이다

**완료 기준:** 무한 루프에 빠지지 않고, 상한·반복에 걸리면 깔끔히 멈추며 그 이유가 트레이스에 남는다.

### M6 — 모델 불가지론 트랜스포트 + qwen3 thinking 처리

control 변수를 흔들 차례. 지금까지 다진 harness 골격 위에서 모델을 바꿔 끼워, harness가
모델 특성을 얼마나 흡수하는지 본다.

**할 일**
- [ ] 트랜스포트를 인터페이스로 추출, 플래그/설정으로 모델 교체 가능하게
- [ ] qwen3:8b의 `<think>` 트레이스를 **로깅엔 남기되 파싱에선 분리**
- [ ] phi4-mini로 같은 태스크를 돌려 thinking 없는 대조군 확보
- [ ] phi4-mini의 빈약한 tool calling이 어디서 더 깨지는지 기록

**생각해볼 것**
- 추론 트레이스 분리를 트랜스포트에서 하나, agent 레이어에서 하나? 모델마다 트레이스 형식이 다르면 어디가 그 차이를 흡수해야 깨끗한가?
- 인터페이스 경계를 어디 긋나? "ollama 전용"으로 짤지, 나중에 OpenAI 호환 API도 끼울 수 있게 추상화할지 — 지금 필요한 만큼만 vs 미리 일반화의 선
- M4에서 정한 structure-first / lenient 선택이 약한 모델에서 다르게 작동하나?

**완료 기준:** 코드 변경 없이 플래그만으로 두 모델을 바꿔 끼울 수 있고, qwen3의 추론 트레이스가 실행 경로를 오염시키지 않는다.

### M7 — 관측성 (구조화 트레이스)

사람들이 가장 많이 건너뛰고 가장 많이 후회하는 부분. 분산 시스템에서 신뢰 불가 컴포넌트를
감싸는 문제(재시도·멱등성·타임아웃·트레이싱)가 전부 여기로 매핑된다.

**할 일**
- [ ] 매 iteration을 구조화 레코드로 기록: 보낸 messages / 받은 raw 응답 / 파싱 결과 / 검증 결과 / 실행한 tool과 결과 / 소요 시간
- [ ] 한 번의 태스크 실행 = 읽을 수 있는 trace 하나 (JSON lines 또는 콘솔 pretty print)
- [ ] 과거에 실패했던 실행을 trace만 보고 원인 진단해보기

**생각해볼 것**
- trace를 코드 곳곳에서 산발적으로 찍을 건가, 한 곳을 거쳐가게 할 건가? 후자가 깔끔하지만 루프 구조에 제약을 건다
- raw 응답을 통째로 남기면 trace가 거대해진다. 무엇을 남기고 무엇을 버릴 건가? (나중에 디버깅할 때 후회 안 할 만큼)
- 사실 M1부터 trace를 깔고 갔다면 M2~M6 디버깅이 훨씬 쉬웠을 것이다. 왜 M7에 배치했는지 — 그리고 다음 프로젝트에선 언제 깔지 — 생각해볼 것

**완료 기준:** "왜 이 실행이 실패/반복했는가"를 코드를 다시 안 읽고 trace만으로 답할 수 있다.

### M8 — 체이닝 태스크로 통합 검증

지금까지 만든 모든 것을 멀티스텝 태스크로 한 번에 시험한다. 그리고 harness가 약한 모델을
얼마나 보상하는지 처음으로 *체감*한다.

**할 일**
- [ ] 멀티스텝을 **강제하는** 태스크 작성. 예: "오늘부터 8월 OMSCS 마감까지 며칠인지 계산하고 거기에 3을 곱해라" (time tool → calculator tool 체이닝 필요)
- [ ] 같은 태스크를 qwen3 / phi4-mini 양쪽으로 실행
- [ ] 성공 여부·재시도 횟수·실패 지점을 비교 기록
- [ ] 태스크 3~5개를 `testdata/tasks.json`에 모아두기

**생각해볼 것**
- "멀티스텝을 강제"하려면 태스크를 어떻게 설계하나? 한 tool로 풀려버리면 의미가 없다. tool 간 의존(앞 결과가 뒤 입력)을 어떻게 박나?
- 성공/실패를 무엇으로 판정하나? 지금은 본인 눈으로 보겠지만, 이걸 자동화하고 싶어지는 순간이 곧 온다 — 그게 다음 단계 신호
- 두 모델의 실패 양상이 다를 텐데, 그 차이가 *모델 능력 한계*인지 *harness 결함*인지 어떻게 구분하나? (클라우드 모델을 control로 잠깐 끼워보는 것도 방법)

**완료 기준:** 동일 태스크에서 두 모델의 행동 차이(성공률·재시도·실패 지점)를 숫자/관찰로 비교한 메모가 있다.

## 다음으로

M8에서 "이 harness 변경이 실제로 도움이 됐나?"를 숫자로 답하고 싶어지는 순간이 온다.
그게 **eval harness**(태스크셋 + 자동 채점 + harness 버전 간 회귀 추적)로 넘어가는 신호다.
`testdata/tasks.json`이 그 출발점이고, harness-lab의 자연스러운 확장이 된다.

**M9 — 프론트엔드 어댑터 (선택).** harness 코어가 `(task) → (trace, answer)` 경계를 깔끔히
노출하고 있다면, 그 위에 CLI 외의 표피를 얇게 얹을 수 있다. Telegram 봇을 붙이면 모바일에서
쓰는 실제 물건이 된다. 이때 처음으로 harness-lab이 "상시 떠 있는 서버"가 되고, ollama와 같은
mini PC(또는 k3s)에 얹으면 모델 호출이 `localhost`로 끝나 빠르다. Telegram은 long polling
방식이면 인바운드 포트 개방 없이 되니 집 네트워크엔 그쪽이 안전하다. 단, 이건 harness 학습이
아니라 메시징 글루이므로 코어가 충분히 단단해진 뒤에.

**코딩 에이전트(Claude Code류) 방향으로 키우려면:** 토이 tool을 `read_file`/`edit_file`/`run_bash`
같은 **부작용 있는 실제 tool**로 교체하고, 그 위에 권한·승인 레이어(M5의 확장)와 코드베이스 규모의
컨텍스트 관리(요약·축출·검색)를 얹으면 된다. 골격은 이미 M1~M7에 다 있다.
